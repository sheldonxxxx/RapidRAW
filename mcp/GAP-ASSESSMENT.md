# Remaining MCP gaps: value and difficulty

This assessment builds on the 2026-09-12 acceptance record and the separately documented [Linux GPU server workflow](REMOTE-SSH.md). Priorities distinguish missing contracts, photographic usefulness and deployment readiness. Executed results and their exact build boundaries are recorded in [VERIFICATION.md](VERIFICATION.md); a checked-in test script alone is not a passing result. Automatic selections are useful starting points when they support the intended local edit. Strict extraction and fine-edge quality require a separate standard.

## Coverage cleanup

The earlier broad acceptance inventory remains **1,893 requirements**. Reclassifying its original successful calls against their recorded schemas corrects seven generic retouch input paths: native-call evidence rises from 657 to 664 requirements, and requirements without evidence fall from 1,226 to **1,219** (161 parameters and 1,058 adjustments). The 1,490 recorded calls, 87 state-assertion rows and 171 pixel-assertion rows are unchanged. No new calls or image-quality credit are created by this repair.

The [reclassification tool](scripts/reclassify-coverage.mjs) preserves the original ledgers, inventory and provenance. The [evidence recorder](scripts/coverage-evidence.mjs) now follows the actual generic/discriminated schema, separates direct input from explicitly asserted derived state, and groups repeated schemas without sharing credit between their individual requirements. New refinement fields belong to the newer build's inventory; its results cannot be silently merged into the older baseline.

Of the old adjustment gaps, 1,030 occur in repeated mask/patch schemas and only 28 lie outside those families. Shared implementation does not remove an input contract, but testing every repeated field independently is a lower priority than proving distinct behavior and representative persistence/forwarding paths.

## Remaining priorities

These are rough effort estimates for one contributor familiar with the fork, including focused verification. They exclude waiting for hardware, accounts or suitable photographs.

| Priority | Remaining work                                                          | Worth doing?                                                                                                        | Difficulty / effort                                                                                     | Minimum useful acceptance gate                                                                                                                                                                                                                                      |
| -------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1        | Broaden guided local-edit acceptance                                    | Yes; directly measures useful editing outcomes                                                                      | Medium; 1–3 days for a small annotated set                                                              | AI-plus-brush repairs and manual masks produce visible intended changes on additional photographs, preserve protected areas, and survive history/restart. The [test plan](testing-matrix.md) keeps guided editing, strict boundary quality, platform support and schema coverage separate. Model research should answer a demonstrated editing need rather than replace an adequate starting selection by default.
